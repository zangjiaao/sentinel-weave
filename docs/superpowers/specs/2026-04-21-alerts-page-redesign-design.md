# Alerts 页面重设计（MVP）设计说明

## 1. 目标与范围

将现有“接入中心（Intake）”重构为“告警（Alerts）”工作台，围绕**任务级告警处理闭环**：

1. 文件上传  
2. 抽样映射预览（后端随机样本 + Agent 推断映射）  
3. 用户确认入库  
4. 仅对该任务触发 Agent 分析  
5. 展示分析进展与成本

MVP 聚焦单页高效率工作流，不做复杂映射编辑器，不做多数据源深度接入。

## 2. 交互与信息架构

页面采用“上输入、下输出”结构。

### 2.1 上半区（操作区）

- 页面标题：`告警（Alerts）`
- Tab：
  - `文件上传`（MVP 实现）
  - `数据对接`（预留占位）
- 文件上传区：
  - 文件选择（CSV）
  - 可选参数（vendor/product/log_type/时间列/规则列/job_id）
  - 按钮：
    - `上传并抽样映射`
    - `确认映射并入库`
    - `分析当前任务`

### 2.2 下半区（观测区）

- 当前任务概览卡：
  - job_id、状态、上传时间、告警总数、已映射/未映射
- 抽样映射结果卡：
  - 后端随机 5 条样本（原始字段）
  - Agent 推断映射摘要（字段映射、默认值、推断原因）
- 分析进展卡（任务级）：
  - run 状态（queued/running/success/failed）
  - 步骤流（fetch → context/suspects → case upsert/link → assessment → notify）
- 成本卡：
  - token（input/output/cached/total）
  - tool 调用次数
  - 耗时（ms/s）

## 3. 后端接口与数据流（MVP）

### 3.1 复用接口

- `POST /api/intake/uploads/import`
  - 上传 CSV
  - 自动默认映射 bootstrap
  - 支持 apply + trigger

### 3.2 前端编排（MVP）

为满足“确认后再入库”，前端流程调整为两阶段：

1. **上传并抽样映射**
   - 上传时 `apply_after_import=false`
   - 创建 job + default map
   - 拉取 job sample（随机样本）
   - 展示“Agent 推断映射摘要”
2. **确认映射并入库**
   - 调用 apply（可 include_unmapped）
   - 展示映射结果统计与问题行
3. **分析当前任务**
   - 触发 patrol（限定当前 job 产生的 ingest events）
   - 返回 run_id 并开始轮询进展与成本

### 3.3 任务级分析约束

- “分析”必须只处理当前任务相关告警（非全局队列）。
- patrol 结果应能追踪到 job 维度的 run，便于 UI 归属展示。

## 4. 错误处理与用户反馈

- 上传失败：展示可读错误（文件格式、字段缺失、服务异常）
- 映射失败：展示 unmapped/error 计数 + 问题样本入口
- 分析失败：展示失败原因（模型/工具/预算/网络）
- 长任务反馈：提供轮询中的进行态与最近更新时间，避免“无响应”感

## 5. 前端实现分层

- `app/alerts/page.tsx`：页面容器与数据加载
- `components/alerts-*.tsx`：拆分操作区、样本区、进展区、成本区
- `app/api/alerts/*`：前端代理路由（与现有 backend API 对接）
- 保留原 `/intake` 路由短期兼容，后续可重定向到 `/alerts`

## 6. 验收标准（MVP）

1. 用户可在 Alerts 页面完成：上传 → 抽样预览 → 确认入库 → 任务级触发分析。
2. 下半区可看到该任务的：
   - 告警数量与映射统计
   - 分析状态与步骤进展
   - token/tool/耗时成本
3. 失败路径有清晰反馈，不出现“卡住无提示”。

## 7. 非目标（MVP 外）

- 复杂可视化映射编辑器（逐字段拖拽/批量规则管理）
- 多数据源实时接入完整链路
- 高级权限、审批流、审计导出

## 8. 风险与后续

- 若任务级触发仍混入全局队列，需要补充后端过滤条件或触发参数。
- 若步骤级进展粒度不足，需要在 run summary/tool calls 上增加结构化字段。
- 下一阶段可扩展为多任务并发视图与历史运行对比。
