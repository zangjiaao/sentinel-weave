# Hermes 长期记忆验证 Spike 设计

- 日期：2026-04-14
- 阶段：Spike / 设计验证
- 状态：待实现

## 1. 背景

当前 PoC 已经验证了以下基础闭环：

- `Hermes + MCP Tool + Skill` 可完成单轮巡检
- Agent 可从告警摘要走到案件、时间线、情报补证、通知预览和报告草稿
- 核心边界已明确：数据库是事实源，`Hermes` 是可替换的 `Runner Adapter`

下一步最关键的问题不再是“单轮分析能否跑通”，而是：

- `Hermes` 是否真的适合持续巡检
- `Hermes memory` 是否能帮助 Agent 跨多轮保持上下文连续性
- 在有噪音和多案件竞争注意力的情况下，Agent 是否还能稳定盯住高价值攻击链

因此，需要一个单独的 Spike 来验证“长期记忆是否有真实收益”。

## 2. Spike 目标与非目标

### 2.1 目标

本轮 Spike 只验证以下问题：

1. `Hermes` 是否能在多轮增量告警中维持案件连续性
2. `Memory Summary` 是否足够有价值，能影响下一轮巡检重点
3. Agent 是否能在噪音较多的情况下持续追踪主攻击链
4. Agent 是否能对多天、多 IP、多目标的攻击活动保持谨慎但连续的判断
5. 当前 `Hermes` 接入方式是否值得继续保留到 MVP

### 2.2 非目标

本轮 Spike 明确不验证以下内容：

- Docker 化部署
- 真实设备对接
- UI/前端
- 正式告警编排系统
- 多 Agent 协作
- 大规模写 Tool 扩展
- 生产级记忆压缩或召回算法

## 3. 核心假设

本轮 Spike 基于以下假设：

1. 结构化事实已经落在数据库中，`Hermes memory` 不承担事实存储职责
2. Agent 当前主要通过读 Tool 获取状态，不直接修改案件主事实
3. 后端仍负责确定性入库、标准化、去重、基础案件归并和事实状态维护
4. `Hermes` 的核心价值在于跨轮次工作记忆，而不是替代后端状态机

如果这些假设不成立，则本轮 Spike 结论无效。

## 4. 设计决策

### 4.1 先读后写

本轮 Spike 默认采用“先读后写”的保守策略：

- 现阶段不扩展大范围写 Tool
- Agent 先只读事实源并输出判断、关注点和记忆摘要
- 如果本轮 Spike 证明记忆确实有用，再补极简写 Tool

### 4.2 事实与记忆分离

必须明确区分：

- **事实状态**
  - `asset`
  - `raw_alert`
  - `normalized_alert`
  - `case`
  - `timeline_event`
  - `evidence`
  - `risk_score_history`
  - `user_feedback`
- **工作记忆**
  - 当前最值得盯的案件
  - 可疑但未证实的关联
  - 下一轮优先补证的对象
  - 最近噪音模式
  - 本轮未解决问题

### 4.3 不扩大 Tool 面

本轮 Spike 使用现有读 Tool 为主，不新增大规模操作类 Tool。

允许保留的下一步候选 Tool 只有以下三类，但本轮默认不实现：

- `case.assessment.save`
- `case.note.append`
- `watchlist.upsert`

这三个 Tool 只面向软状态和工作结论，不允许直接改写案件主事实。

## 5. Spike 输入设计

### 5.1 输入方式

本轮 Spike 继续使用本地样例数据，不接真实设备。

输入方式分为两层：

- **基础种子**
  - 资产数据
  - 初始案件与时间线
  - 初始情报缓存
- **增量批次**
  - 按轮次导入的新告警
  - 包含真实攻击动作与噪音混合样本

### 5.2 噪音类型

为了让验证更贴近真实值守，本轮 Spike 应显式加入以下噪音：

- 高频失败漏扫
- 重复或轻微变体告警
- 高误报率规则命中
- 健康检查或探针流量
- 同一资产在不同设备中的多命名
- 代理 / CDN / 反向代理导致的源地址变化
- 与主案件时间接近但本质无关的普通异常

### 5.3 主攻击链

本轮 Spike 的主攻击链采用多天、多 IP、多阶段路径：

1. 第一天：攻击者使用 `IP1` 对 3 个系统打点和探测
2. 第二天：攻击者利用其中 1 个系统漏洞写入 `WebShell`
3. 第三天：攻击者改用 `IP2` 连接 `WebShell` 并执行命令
4. 后续轮次：出现横向准备、短暂静默、重新活跃等变化

此攻击链必须与噪音混合出现，不能单独裸跑。

### 5.4 次要干扰案件

除了主攻击链，还应加入一个低到中风险的次要干扰案件，用来验证 Agent 的注意力分配能力。

该干扰案件建议具备以下特征：

- 与主案件时间接近
- 也会连续出现 `2` 到 `3` 轮
- 有一定可疑性，但证据链不完整
- 更容易被解释为失败扫描、低质量攻击或误报堆叠

预期不是让 Agent 忽略它，而是验证：

- Agent 能同时维护“主案件”和“次要案件”
- Agent 能正确把主案件放在更高优先级
- `Memory Summary` 不会被次要案件完全占满

## 6. 多轮巡检设计

建议至少跑 `6` 轮，每轮只注入增量数据。

### 6.1 Round 1：侦察启动

包含：

- 真正的外部探测与路径打点
- 多条失败漏扫
- 常见低价值规则触发

预期：

- Agent 能识别“存在值得观察的潜在案件”
- 不会因为单次扫描就直接给出过度确定的结论
- `Memory Summary` 应记录需要重点跟踪的资产、来源或模式

### 6.2 Round 2：利用成功

包含：

- 真实漏洞利用与 `WebShell` 写入
- 同时间窗口的噪音延续

预期：

- Agent 能将本轮事件与上一轮侦察活动串联
- 案件风险明显升级
- 记忆中应保留“该资产已进入成功利用阶段”的结论

### 6.3 Round 3：新 IP 接管

包含：

- 新 IP 连接既有 `WebShell`
- 命令执行相关告警
- 伴随源地址变化和代理型噪音

预期：

- Agent 不因为 IP 变化直接拆案
- 能表达“高度相关，但仍保留不确定性”
- 记忆中应保留“新 IP 与既有攻击链相关联”的跟踪结论

### 6.4 Round 4：横向准备

包含：

- 内网扫描或横向准备线索
- 少量主机侧低价值事件

预期：

- Agent 能将案件阶段推进到更高风险态
- 能明确指出主证据和未证实部分

### 6.5 Round 5：静默期

包含：

- 无显著新攻击动作
- 仍有少量低价值背景噪音

预期：

- Agent 不会因为短期沉默直接把案件降为无风险
- 记忆应保留 watchlist 与未完成调查事项

### 6.6 Round 6：重新活跃或补证

包含：

- 新一轮可关联证据，或能补强既有判断的新事件

预期：

- Agent 能快速承接前几轮上下文
- 不需要重新从零建立攻击画像

## 7. 验证重点

本轮 Spike 关注以下四类能力：

### 7.1 连续性

- 能否跨轮次盯住同一个案件
- 能否把新告警映射到既有攻击链
- 能否避免每轮都像首次见到该案件一样重新分析
- 能否同时维持主案件与次要干扰案件的优先级

### 7.2 抗噪能力

- 是否会被高频低价值告警带偏
- 是否能在噪音中保留主攻击链的优先级
- 是否能清楚区分噪音与高价值证据

### 7.3 记忆质量

- `Memory Summary` 是否具体、可复用、可指导下一轮
- 记忆内容是否聚焦 watchlist、未解问题和阶段性判断
- 记忆是否避免写入原始事实细节或重复数据库内容

### 7.4 表达质量

- 是否清楚区分事实、推断和不确定性
- 是否能解释为什么认为多个事件相关
- 是否能在 IP 变化、资产别名和设备差异下保持审慎表达

## 8. 结果判定

### 8.1 通过

如果满足以下条件，可认为本轮 Spike 通过：

- 多轮巡检中，Agent 能连续维护主案件
- `Memory Summary` 明显帮助下一轮聚焦分析
- Agent 在有噪音时仍能抓住主攻击链
- 不依赖 `Hermes memory` 存事实也能完成连续研判

### 8.2 部分通过

以下情况视为部分通过：

- 能连续关注案件，但经常被噪音干扰
- 能写出记忆摘要，但对下一轮帮助有限
- 多轮串联基本成立，但对 IP 变化或资产别名处理不够稳

这种情况下，优先优化：

- 噪音样本
- Skill 指令
- 记忆摘要格式
- 事实检索顺序

### 8.3 不通过

以下情况视为不通过：

- 每轮都像从零开始，几乎没有连续性
- 记忆对分析结果没有明显帮助
- Agent 明显被噪音主导，抓不住主案件
- `Hermes` 需要承担过多事实状态维护才能勉强工作

如果不通过，应重新评估是否继续采用 `Hermes` 作为长期巡检运行时。

## 9. 下一步策略

本轮 Spike 完成后，根据结果进入不同分支：

- **通过**：进入“极简写 Tool Spike”，验证 `case.assessment.save` / `watchlist.upsert`
- **部分通过**：先调样本、Skill 和巡检策略，再复测一轮
- **不通过**：考虑以 `OpenAI SDK Runner + 自建记忆层` 替代 `Hermes`

## 10. 实施边界

为了控制 Spike 范围，本轮必须遵守：

- 不扩展真实设备接入
- 不引入 Docker 或部署设计
- 不做正式前端
- 不做复杂多 Agent
- 不实现大范围写 Tool
- 不改变“数据库是事实源”的原则

本轮唯一需要回答的问题是：

> 在持续巡检这个具体场景下，`Hermes memory` 是否真的值得保留到 MVP。
